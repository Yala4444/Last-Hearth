# Last Hearth v0.15 — Dev Plan
Status: planned, waiting for playtest screenshots/notes to merge before implementation.
Base: v0.14.1

## Product goal
Turn the current prototype into a clearer, more physical and more satisfying vertical slice:
1. The first 60–120 seconds must feel like the playable mobile-game ad promise.
2. The Last Hearth must feel like a real place the player physically develops, not a menu with drawings.
3. Every choice must communicate its consequence before and after selection.
4. A failed run must feel earned and understandable.
5. The Forgotten Forest should remain varied without becoming mechanically noisy.
6. The build should be stable and readable on iPhone portrait before adding the next large region.

## Core fantasy
Darkness has extinguished old fires and split survivors apart. The player carries the light outward, restores field fires, rescues people, brings them home and physically grows the Last Hearth from a tiny refuge into a settlement. Every recovered fire pushes the darkness farther away.

## A. Last Hearth — full hub readability pass
### A1. Physical traversal
- Preserve left = grove/wood, right = quarry/stone.
- Enter a side area from one edge and appear on the opposite edge of the connected area.
- No instant return/bounce after transition.
- Require the player to move away from the entrance before the return trigger arms.
- Add short 0.18–0.28 s fade/slide so the transition reads as moving through one world.
- Keep the player, carried resources and followers spatially consistent through transitions.

### A2. Central settlement composition
Re-layout the hub so it reads in layers:
- top: map / expedition table;
- upper-left, upper-middle, upper-right: homes/construction lots;
- center: Last Hearth;
- lower-left: backpack/storage permanent upgrade;
- lower-right: weapon permanent upgrade;
- lower-center: hearth permanent upgrade;
- bottom-left: Hearth Book/help.
No two labels may overlap at 480x854 logical viewport.

### A3. Construction visuals
Replace abstract scaffolds with a clear construction state machine:
- empty footprint;
- stakes/foundation;
- frame;
- partial walls;
- roof;
- finished house.
Only show detailed material counters when the player is near the site.
From distance show one short label only, e.g. “ДОМ ОХОТНИКА”.

### A4. Construction interaction
- Wood/stone physically leaves the player and flies/steps into the target construction.
- One unload pulse per material chunk.
- Build stage changes exactly when thresholds are crossed.
- Completion: short hammer/build effect, light pulse, resident reaction, one clean banner.
- No modal interruption for ordinary deliveries.
- Persist partial progress.

### A5. Residents
Residents should have readable home/role relationships:
- forester spends time near forester house / grove path;
- hunter near hunter house / edge of settlement;
- master near workshop/upgrade area;
- scout/guards occupy perimeter positions later.
Do not stand NPCs on top of building labels.
After a building completes, its resident should visibly relocate to it.

## B. Settlement progression: 0/3 → 3/3 forest fires
The hub must materially change after every successful forest signal.

### Stage 0 — Refuge
- tiny central fire;
- map table;
- almost empty clearing;
- no finished homes;
- limited light radius.

### Stage 1 — Camp
- larger fire/light radius;
- first construction lots become active;
- rescued residents return;
- grove/quarry become useful for construction;
- visible population: 2–4.

### Stage 2 — Outpost
- second visual ring of settlement becomes active;
- more props: woodpile, crates, lantern poles, defensive stakes;
- one perimeter resident/guard;
- new permanent-upgrade visual state;
- night-defense history is visible in the camp.

### Stage 3 — Settlement
- 3/3 forest fires visibly linked to the Last Hearth;
- stronger central hearth visual;
- several finished/active buildings;
- perimeter markers / watch element;
- map clearly indicates Forgotten Forest complete and next darkness beyond it.
No fake “new region unlocked” claim until that region is actually playable.

## C. Choice clarity — before, during and after
### C1. Before the choice
Every route label uses:
NAME • PRIMARY REWARD
Examples:
- ОХОТНИК • СОЮЗНИК
- ЛОГОВО • УРОН
- СКЛАД • ЗДОРОВЬЕ/СЛОТ
- АЛТАРЬ • УРОН
- БАРРИКАДА • ОЧАГ
Use compact labels that fit without covering the world.

### C2. Risk communication
If a route has no ally and the player currently has no companion:
- show a small warning near the route: “РИСК: НОЧЬ В ОДИНОЧКУ”.
- do not block the choice.
- do not secretly rebalance it into an easy route.
The player can deliberately choose power over safety.

### C3. After the reward
Never say only “equipment improved”.
Show the concrete change:
- УРОН 22 → 28
- ЗДОРОВЬЕ 100 → 124
- СЛОТЫ 5 → 6
- ОЧАГ 185 → 223
- СОЮЗНИК +1
Keep it visible long enough to read but do not stack with another notification.

### C4. Run build strip
Outside resource-building phases, HUD should expose the current build compactly:
- damage;
- max HP;
- carry slots;
- companion count / companion icon.
Optional status chips for major temporary powers:
- огненные стрелы;
- дозор;
- баррикада.
Do not add a full RPG inventory screen in v0.15.

## D. Companions must visibly matter
### Hunter
- ranged attacks;
- visibly fires from near player/hearth;
- small distinct projectile style.

### Worker
- lower combat output;
- periodically repairs a small amount of hearth HP during nights OR improves defensive structure effectiveness.
Choose one simple readable role, not both.

### Scout/Guard
- faster shots / marks incoming side / short pre-wave warning.
Again: one identity per role.

### Feedback
- companion attacks are visually distinct but subdued;
- night-start card can say “Союзники: 2”;
- defeat screen explicitly explains when a solo route materially contributed to failure.

## E. Night defence readability
- Pre-night 1.5–2 s preparation beat.
- Show active attack directions with edge warning markers before enemies fully enter.
- Do not let direction labels overlap story cards.
- Give elite/boss a clear silhouette and health bar.
- Keep the hearth as the obvious defense objective.
- If player dies vs hearth dies, result text must explain which happened.
- Night 2 may remain very hard solo; it must be telegraphed, not hidden.

## F. Notification/UI architecture
Replace independent overlapping messages with one priority queue:
priority 1: critical tutorial / choice consequence;
priority 2: story/event result;
priority 3: stage banner;
priority 4: small pickup/build feedback.
Rules:
- only one large card at a time;
- banner waits while story card is visible;
- small feedback uses a fixed safe lane;
- world labels fade/hide when under a large card;
- max 2 lines for route labels, max 4 lines for story cards;
- respect top browser/safe-area visual space.

## G. “Playable ad” first-session loop
The first session must be intentionally choreographed:
1. Spawn in darkness with one visible tree.
2. Chop tree.
3. Logs visibly fall.
4. Pick them up.
5. Carry to field fire.
6. Fire grows and darkness retreats.
7. Two route choices appear.
8. One route clearly promises an ally.
9. Rescue ally.
10. Ally follows the player.
11. Night begins and ally visibly helps.
12. Return to Last Hearth.
13. Player sees an empty construction lot and learns that rescued people need a home.
This sequence should be understandable with minimal reading and should be usable almost frame-for-frame in an ad.

## H. First-session tutorial
Keep tutorial contextual instead of a long modal.
- movement prompt;
- chop prompt;
- pickup/carry prompt;
- deliver to fire;
- choose route;
- rescue/return;
- defend hearth;
- after first return: build at Last Hearth.
Hearth Book remains available for full explanation.
Tutorial text should disappear permanently once the action is demonstrated.

## I. Forgotten Forest variation pass
Keep the three-sector structure but ensure each has a distinct identity.

### Sector 1 — Edge / tutorial
Readable, simple, human:
- hunter vs sawmill;
- worker ruins;
- watch vs altar.

### Sector 2 — Old road
Risk/reward:
- caravan ally vs nest damage;
- old storehouse;
- barricade vs stone circle.

### Sector 3 — Heart of forest
Mystery/pressure:
- signal survivor vs dead fire;
- scout;
- beacon vs guard cache.
Each sector gets:
- distinct background silhouette;
- distinct landmark;
- distinct route copy;
- at least one ally opportunity somewhere in the sector.
Do not reuse a sawmill/watch scaffold under a different label.

## J. Economy and permanent progression
Clarify currencies:
- wood/stone = physical settlement construction;
- embers = permanent upgrades;
- temporary expedition buffs reset after run.
Permanent upgrade stations:
- Backpack: carry slots;
- Weapon bench/armory: base damage;
- Hearth: base hearth HP + light radius.
Show current effect and next effect before spending.
Example:
“РЮКЗАК ур.1 — 6 слотов → ур.2 — 7 слотов | 5 углей”

## K. Reward pacing
A run should regularly deliver visible “payoff moments”:
- light radius expansion;
- rescued follower;
- build completion;
- concrete stat jump;
- new visual in settlement;
- recovered signal/fire;
- settlement stage upgrade.
Avoid rewards that exist only as text/numbers.

## L. Result screen
Success:
- what fire was restored;
- run path history;
- rescued people;
- important upgrades found;
- embers gained;
- settlement change preview.
Failure:
- cause: hero died / hearth died;
- path history;
- concrete lesson if relevant (“no companion”, “hearth too weak”, etc.);
- embers retained;
- one clear return action.
No misleading “next region” line before actual unlock.

## M. Mobile visual QA
Target portrait 480x854 logical canvas / iPhone browser:
- no clipped labels;
- no text under Safari chrome assumptions;
- no building label overlaps;
- no route label >2 lines;
- no unreadable 7–8 px text for critical information;
- tap/movement zones do not conflict with edge transition zones;
- player must be able to reach every gate with touch movement.

## N. Technical cleanup
- Extract hub transition state into explicit enter/armed/return logic.
- Centralize reward application helpers so stat changes and UI copy cannot disagree.
- Centralize notification queue.
- Add helper for “before → after” stat messages.
- Keep save migration safe from v0.13/v0.14.
- Version as v0.15 only after tests pass.

## O. Automated tests required before deploy
1. Hub traversal through real _process loop:
   center → grove → move inward → return;
   center → quarry → move inward → return.
2. Construction delivery and persistence for each available house.
3. No route in sector 2/3 falsely advertises an ally without adding one.
4. Solo Night 2 warning appears when survivors == 1.
5. Backpack/weapon/hearth upgrades change the expected stats.
6. Temporary run buffs reset; permanent buffs persist.
7. All 3 forest sectors can reach a result screen.
8. Web export + boot test.
9. Existing progression and visual tests remain green.

## P. Acceptance criteria
v0.15 is ready only when:
- the Last Hearth can be navigated without bounce-back;
- hub labels are readable on mobile;
- construction objects visually read as buildings under construction;
- player can explain what backpack, weapon and hearth upgrades do without opening the code/help;
- every major route choice shows its main reward before selection;
- every major reward shows an explicit effect after selection;
- a solo Night 2 loss feels understandable;
- first-session playable-ad loop is coherent from chop → light → ally → night → home;
- CI is fully green and GitHub Pages deployment succeeds.

## Playtest merge rule
Before implementation begins, merge the next user screenshots and spoken observations into this plan:
- visual/UI defects become P0/P1 fixes;
- gameplay confusion becomes choice/tutorial/feedback requirements;
- bugs become regression tests first;
- new feature ideas are added only if they reinforce the core loop and do not destabilize the v0.15 vertical slice.
